# 01 — АНАЛИЗ ЗАГРУЗЧИКА RustSecure.exe

Цель: понять обфускацию, расшифровать 112 строк (URL/пароли/sharedSecret), найти ключи.

---

## 1. Общая картина

- `RustSecure.exe` — managed .NET сборка (CLR), **не нативная**.
- Обфускатор: **Agile.NET / CliSecure-семейство**.
- Точка входа `Main` — в классе `MeterFrameIntervalManager`.
- Обфускатор **сохранил реальные имена методов/типов**, но переименовал пространства имён
  в мусор — это наш рычаг: реальные названия (например `SynchronizeFrameUpdateValidator`,
  `ForecastFrameLoad.InjectNativeAndRunCore`) читаются прямо в метаданных.

## 2. Поток выполнения Main (установленная последовательность)

1. обработчики исключений (try/catch глобально);
2. мьютекс single-instance (защита от повторного запуска);
3. `PrivacyConsentForm` — форма согласия;
4. проверка VC++ redistributable;
5. анти-отладка / анти-VM проверки;
6. **скачивание payload'ов** с сервера через `SynchronizeFrameUpdateValidator`
   (Core payload + Native payload; данные шифруются, расшифровываются, валидируются как DLL);
7. `AssessFrameQuality` — закрывает процесс Rust;
8. запуск Rust;
9. ожидание модуля;
10. `ForecastFrameLoad.InjectNativeAndRunCore` — инжект payload'а;
11. загрузчик завершается.

## 3. Две VM для расшифровки строк

### 3.1. 25-опкодная стековая VM — метод 0x8A2 `ODCuBUBLJtbV`
- Интерпретирует байткод **FLD[1436]** (459 байт) с массивом делегатов **FLD[1013]**.
- Возвращает `byte[]`.
- `arg1` = размер массива (**16 = IV**, **32 = ключ**), `arg0` = исходные данные.
- **Рабочий эмулятор написан**: `vm_emulator.py` (опкоды 1..25, хэндлеры UTF8/Empty/GetBytes).

### 3.2. 82-опкодная VM — метод 0x89E `awhuBmgthIGH` (главный дешифратор строк)
- **160+ вызовов** → это и есть расшифровщик 112 строк.
- 4857 инструкций IL; диспетчер через бинарный поиск по порогам опкодов 1/2/5/10/20/41/82.
- Полный дамп IL: `il_089e.txt` (с разрешёнными именами полей/методов/строк).
- Формат инструкции байткода: `опкод(1 байт) + операнд int32` → **9-байтные инструкции**
  (`ptr += 1` на опкод, операнд читается как `int32` при `ptr+4`, затем `ptr += 8`).

## 4. Поля FieldRVA (роли установлены)

| FLD | Тип / роль |
|-----|-----------|
| FLD[1006] | `string[]` — зашифрованные строки (112 шт) |
| FLD[1009] | `IntPtr[]` — обработчики/делегаты |
| FLD[1013] | массив делегатов (для 25-опкодной VM) |
| FLD[1431] | **байткод** (bytecode) |
| FLD[1432] | **таблица узлов** — красно-чёрное дерево поиска |
| FLD[1436] | байткод 25-опкодной VM (459 байт) |

Размер FieldRVA = разница между соседними RVA (см. `get_fields()` в любом скрипте).

## 5. Зашифрованные строки

- **112 строк** base64 по файловому смещению **`0x2d0385`**.
- Каждая 44 символа = 32 байта = **2 блока AES**.
- Шифрование: **AES-256-CBC** (ключ 32 байта, IV 16 байт).
- Расшифровываются 82-опкодной VM (метод 0x89E) при старте.

## 6. Дерево FLD[1432] — НЕ ключ (важный вывод)

- Формат записи (8 байт): `00 00 F V V F 00 00` → 16-битное значение `(F<<8)|V`.
  Или `ff ff ff ff ff ff ff ff` = NULL (-1).
- Int32 по смещению entry+4 = `(F<<8)|V`.
- Значения — **арифметические последовательности** (0x170,0x150,0x130,0x110,0xF0;
  0x5F5,0x623,0x651,0x67F,0x6AD; 0x30,0x60,0x90,0xC0) → это **таблица поиска
  (индексы/смещения)**, а НЕ источник AES-ключа.

## 7. ГДЕ ключ AES (32B) + IV (16B) — СТАТУС

Ключ и IV зашиты как непосредственные значения в байткоде **FLD[1431]**.

### ✅ Результат проверки XOR-гипотезы (ВЫПОЛНЕНО 2026-08-15)
`xor_bc.py` запущен. **XOR-гипотеза ОПРОВЕРГНУТА** — байткод НЕ зашифрован простым XOR
(`37 ad a0 fe` даёт мусор).

### 🔎 Что видно в сыром байткоде FLD[1431] (дамп первых 128 байт)
```
0000  01 00 00 00 00 00 00 00 00 02 00 00 00 24 24 00 00 00 00 00 00 1a 1a 00 00 00 03 00 00 00 01 01
0020  00 00 00 04 05 00 00 00 02 02 00 00 00 06 00 00 00 7c 7c 00 00 00 00 00 00 61 61 00 00 00 52 00
```
- Данные **уже структурированы** (не случайные, не XOR-мусор).
- Мелкие целые `01 02 03 04 05 06 07 08 09 …` — похоже на **опкоды**.
- **Паттерн «удвоенных байт»**: `24 24`, `1a 1a`, `7c 7c`, `61 61`, `01 01`, `02 02`, `85 85` —
  реальный байт записан **дважды** (де-дупликация = взять каждый 2-й байт).
- «Магический» палиндром `37 ad a0 fe fe a0 ad 37` на 0x8e/0xc7 — вероятно, НЕ ключ XOR,
  а часть данных/таблицы.

### Что делать дальше (для нового контекста)
1. Снять полный дамп FLD[1431] (`dump_keydata.py`).
2. Определить точный формат: 9-байтные инструкции (опкод + int32-операнд) ИЛИ
   «удвоенный байт». Сравнить с диспетчером 0x89E (бинарный поиск по порогам опкодов).
3. Применить де-дупликацию (`data[::2]` или `data[1::2]`) и проверить, складываются ли
   инструкции в валидные опкоды 1..82.
4. Вынуть 32B ключ + 16B IV (как непосредственные значения байткода).

## 9. Полезные константы IL-токенов

- MemberRef = 0x0A, MethodDef = 0x06, Field = 0x04, TypeRef = 0x01, string = 0x70, StandAloneSig = 0x11.
- Сигнатуры полей: 0x06=FIELD, 0x05=U1(byte), 0x11=VALUETYPE, 0x12=CLASS, 0x15=GENERICINST, 0x1d=SZARRAY, 0x0e=STRING, 0x18=I(native int).

## 10. Подводные камни dnfile/dncil (чтобы не терять время)

- У `TypeDef` строки: `r.TypeName` / `r.TypeNamespace` (атрибута `Name` нет).
- У тела метода (`dncil`): `b.max_stack` (НЕ `maxstack`); атрибута `b.locals` нет.
- `md.UserString` не существует; `md.UserStrings` тоже (в этой версии dnfile) — строки из #US доставать иначе.
- `ClrFieldAttr` нельзя форматировать через f-string/`int()` — выбросить flags из вывода.
- PowerShell 5.1: here-string `@"..."@` ломает кавычки внутри Python f-строк → **писать Python в файл через Write, а не `python -c`**.
