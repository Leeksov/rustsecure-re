# 03 — АНАЛИЗ RustSecure.Core.dll (Core payload)

Цель: деобфусцировать, отделить мусор от логики, найти методы защиты и инжект-логику.

---

## 1. Что это за файл

- **`RustSecure.Core.dll`** — управляемая .NET сборка (**`Assembly: RustSecure.Core`, версия 1.0**).
- Это **Core payload**, который сервер отдаёт по `/api/loader/core` (уже в расшифрованном виде,
  выдан клиентом). Размер **19 261 952 байта (~19.2 МБ)**.
- **Точки входа нет** (`EntryPointToken = 0x0`) → это библиотека (DLL), а не EXE.
  Инжектится в процесс Rust и вызывается извне.

## 2bis. ВНЕШНИЕ ЗАВИСИМОСТИ (15 AssemblyRef — получено 2026-08-15)

Все — стандартные .NET Framework, **нет стороннего анти-чит SDK** (BattlEye/EAC и т.п. НЕТ):

| Assembly | Что даёт |
|----------|----------|
| mscorlib / System / System.Core / netstandard | базовый рантайм |
| System.Net.Http | **связь с сервером** |
| System.Management | **WMI** — сбор железа / HWID / детект VM |
| System.Reflection.Metadata + System.Collections.Immutable | рантайм обфускатора Agile.NET / рефлексия метаданных |
| System.Numerics | математика (крипто/хэши) |

| System.Data / System.Configuration / System.Xml / System.ValueTuple | стандартное |

Вывод: Core.dll — **самодостаточный .NET-модуль** без внешних SDK; обфускация + серверная
валидация реализованы вручную. Для детекта используются WMI (HWID/VM) и, вероятно,
`System.Reflection.Metadata` (манипуляция IL/метаданными).

> 897 TypeRef ещё не сгруппированы (`dump_refs.py` падает на unhashable `HeapItemString` —

## 3. Что делать поочерёдно

### Шаг 1 — Дамп внешних зависимостей (что эта DLL делает)
Запустить `dump_refs.py` (уже написан). Он выведет:
- **15 AssemblyRef** — какие библиотеки используются (анти-чит SDK? драйверная связь?
  System.Net.Http? DllImport native?).
- **897 TypeRef** — внешние типы, сгруппированные по namespace.
  По этому списку сразу видно: работа с процессами (инжект), HWID (сбор железа),
  сеть (связь с бэкендом), анти-отладка и т.д.

### Шаг 2 — Снять карту реальных имён
Обфускатор сохраняет реальные имена методов/типов (переименованы только namespace).
Сгруппировать TypeDef по `TypeNamespace`/`TypeName`, отфильтровать мусорные
(короткие рандомные имена) от осмысленных (`...MeterFrameIntervalManager`,
`SynchronizeFrameUpdateValidator`, `ForecastFrameLoad` и т.п.).

### Шаг 3 — Найти строки и их расшифровщик
- В Core.dll, скорее всего, **та же 82-опкодная VM** для строк.
- Найти метод-дешифратор (по сигнатуре: бинарный поиск по порогам опкодов,
  как в RustSecure.exe метод 0x89E).
- Выгрузить зашифрованные строки (FieldRVA / #US) и расшифровать тем же способом.

### Шаг 4 — Локализовать логику защиты и инжекта
Искать по реальным именам (см. 04-файл): HWID, license, anti-debug, anti-VM, inject.

### Шаг 5 — Найти экспортируемые точки вызова
Т.к. это DLL без entry point, инжектор (Native payload) зовёт конкретные managed-методы.
Найти их (например по `[DllExport]` / именам-контрактам) — это «вход» в логику античита.

## 4. Заметки по инструментам

- 84 077 методов — нельзя дампить все сразу; работать выборкой по реальным именам.
